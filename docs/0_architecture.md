# Six Sorting Hat - 육모자 애플리케이션 구현 기획

## 0.개요
여섯 색깔 모자 기법은 세계적인 컨설턴트이자 창의성 분야의 권위자인 에드워드 드 보노(Edward de Bono)가 개발한 사고 기법입니다. 이 기법은 복잡한 문제에 대해 여러 사람이 동시에 다른 관점에서 생각하며 발생하는 비효율과 갈등을 방지하고, 특정 시점에는 하나의 관점에만 집중하여 논의를 진행함으로써 보다 명료하고 생산적인 결과를 도출하기 위해 고안되었습니다.

참가자들은 여섯 가지 색깔로 구분된 가상의 '사고 모자'를 번갈아 쓰는 상징적인 행위를 통해, 각 모자가 대표하는 특정 유형의 사고에만 집중하게 됩니다. 이를 통해 개인의 성향이나 감정에 치우치지 않고, 주제에 대한 다각적이고 균형 잡힌 탐색이 가능해집니다.

### 각 색깔의 모자는 다음과 같은 고유한 사고의 방향을 나타냅니다.
#### 하얀 모자 (White Hat): 정보와 사실
역할: 객관적인 정보와 데이터에 집중합니다.
주요 질문: "우리가 무엇을 알고 있는가?", "어떤 정보가 필요한가?", "이것은 사실인가, 아니면 가정인가?"
특징: 감정이나 의견을 배제하고 중립적인 입장에서 사실과 수치를 기반으로 사고합니다.

#### 빨간 모자 (Red Hat): 감정과 직관
역할: 직감, 감정, 예감 등 주관적인 느낌을 표현합니다.
주요 질문: "이 문제에 대해 어떻게 느끼는가?", "나의 직감은 무엇을 말하고 있는가?"
특징: 논리적인 근거나 설명을 요구하지 않고, 순수한 감정의 표현을 허용합니다. 이를 통해 논의에 인간적인 요소를 더하고, 중요한 직관을 포착할 수 있습니다.

#### 검은 모자 (Black Hat): 위험과 비판
역할: 잠재적인 문제점, 위험, 약점, 부정적인 측면을 찾아냅니다.
주요 질문: "무엇이 잘못될 수 있는가?", "가장 큰 위험 요소는 무엇인가?", "이 계획의 약점은 무엇인가?"
특징: 논리적인 근거에 기반한 비판적 사고를 통해 신중한 판단을 돕습니다. '악마의 변호인' 역할을 수행하며 잠재적 실패 가능성을 줄입니다.

#### 노란 모자 (Yellow Hat): 긍정과 낙관
역할: 아이디어나 제안의 긍정적인 측면, 이점, 기회를 탐색합니다.
주요 질문: "이것의 장점은 무엇인가?", "어떤 긍정적인 결과가 기대되는가?", "어떻게 실행 가능하게 만들 수 있는가?"
특징: 밝고 긍정적인 시각으로 가치와 가능성을 발견하고, 아이디어를 발전시킬 동기를 부여합니다.

#### 초록 모자 (Green Hat): 창의성과 새로운 아이디어
역할: 기존의 틀에서 벗어나 새로운 아이디어, 대안, 가능성을 제시합니다.
주요 질문: "다른 방법은 없을까?", "전혀 새로운 아이디어가 있는가?", "이것을 다르게 보면 어떨까?"
특징: 창의적이고 모험적인 사고를 장려하며, 브레인스토밍과 같이 자유로운 아이디어 생성을 촉진합니다.

#### 파란 모자 (Blue Hat): 사고의 관리와 통제
역할: 전체적인 사고 과정을 관리하고 통제하는 사회자 역할을 합니다.
주요 질문: "우리의 논의 목표는 무엇인가?", "지금 어떤 모자를 써야 할까?", "다음 단계는 무엇인가?"
특징: 회의의 시작과 끝을 주관하며, 논의의 방향을 설정하고, 다른 모자들의 사용 순서를 결정합니다. 오케스트라의 지휘자처럼 전체적인 사고의 흐름을 조율합니다.

육모자 애플리케이션은 이 사고 기법을 사람이 아닌 LLM 이 활용하면 어떨까? 를 바탕으로 설계되고 기획 되었습니다.
6개의 LLM 모델이 각자의 역할을 받아 사고를 확장한다면 사용자는 더 많은 아이디어와 창의력을 가질 수 있지 않을까?
내가 보지 못한 시점을 육모자 애플리케이션을 통해 볼 수 있지는 않을까?

여섯 색깔 모자 기법을 활용한 멀티 LLM 챗봇 시스템 설계 백서
## 섹션 1: 개념적 프레임워크: 여섯 색깔 모자 멀티 에이전트 패러다임

## 섹션 2: 핵심 아키텍처: 멀티 에이전트 대화 엔진 설계
본 섹션에서는 애플리케이션의 기술적 중추를 상세히 설명합니다. 특정 멀티 에이전트 프레임워크 선택의 타당성을 입증하고, 에이전트 토론을 조율하기 위한 완전한 아키텍처를 개괄합니다.

### 2.1. 프레임워크 선택: LangGraph
LangChain의 LangGraph는 워크플로우를 명시적인 노드와 엣지를 가진 그래프로 모델링하는 상태 기반 오케스트레이션 프레임워크로, 상호작용의 순서와 상태에 대한 세밀한 제어를 제공합니다.
state에 따른 node와 edge 구조를 활용 하여 질의-답변 상태 관리와 순환 구조를 완성해야 합니다.

### 2.2. 아키텍처 청사진: 슈퍼바이저 주도형 그래프
아키텍처는 LangGraph의 StateGraph를 기반으로 설계됩니다. 주요 구성 요소는 다음과 같습니다.  

#### 상태 객체 (State Object): 전체 대화 기록, 사용자의 초기 질의, 현재 모자 할당 상태, 토론의 현재 진행 상황을 포함하는 중앙 집중식 영구 객체입니다. 이 객체는 그래프의 모든 노드 간에 전달되며 대화의 상태와 노드의 이동을 관리합니다.

#### 에이전트 노드 (Agent Nodes)
- 각 '모자'에 해당하는 6개의 개별 노드입니다. 각 노드는 현재 상태를 입력받아, 할당된 LLM을 적절한 프롬프트로 호출하고, 그 응답을 반환하는 함수로 구현됩니다. 
- 모자들은 이전 답변을 참고하여 답변을 좀 더 확장합니다. userinput -> 빨간 모자 답변 -> userinput + 빨간 모자 답변 + 하얀 모자 답변 ... userinput + 모든 모자 답변 + 파란 모자 정리
- 각 모자들은 이전의 답변을 참고하여 자신만의 특색있는 사고방식을 활용하여 답변을 확장합니다.
- 파란 모자는 이전 대화들을 최종적으로 정리하여 userinput에 맞는 답변인지 검증하고 답변의 품질을 체크합니다.
- 답변 검증과 품질에 합격하면 최종 답변으로 사용자에게 전달 합니다.
- 답변 검증과 품질에 불합격 하면 다시 각 모자들에게 질의를 넣어 답변을 확장합니다.
- 재질의 때는 쿼리를 확장하여 답변 품질을 높힙니다.
- 모자들의 답변 순서는 매 시도마다 달라야 합니다.

#### 조건부 엣지 (Conditional Edges): 노드 간의 연결은 조건부로 설정됩니다. 파란 모자의 출력이 어떤 엣지를 따라갈지 결정하며, 다음으로 적합한 에이전트 노드로 제어권을 라우팅합니다.
- 에이전트 노드는 StrOutputparser() 를 활용하여 구조화된 답변을 출력합니다.
- 구조화된 답변은 엣지를 타거 적합한 에이전트 노드로 라우팅 됩니다.

#### Langchain Tool
- 각 모자 노드는 MCP SERVER 를 Tool 로 활용하여 필요에 따라 웹검색, 크롤링 등을 진행합니다.
- Mcp Server 가 아니더라도 활용 가능한 유용한 Tool 에 대한 고민이 필요합니다.
- llm 은 Tool 과 결합되어 상황에 맞춰 랭그래프 노드에서 활용됩니다.

#### 의도 분류 모델
- 간단한 인사, 정체성 문의 등에 대해서는 첫 의도분류를 통해 분류합니다.
- 문제 해결, 답변이 필요한 질문, 아이디어 확장 등의 의도에 대해서만 6개 모자 로직을 태웁니다.

#### 2.3. 전문화된 역할을 위한 LLM 선택 전략
- 모든 LLM이 동일한 성능을 보이는 것은 아닙니다. 모델마다 특정 작업에 대한 강점이 다르므로 , 각 모자의 기능과 모델의 강점을 일치시켜 성능과 비용을 최적화할 수 있습니다.   
- 다만 초기 mvp 모델에서는 gpt-4o-mini 모델만을 활용합니다.

## 섹션 4: 시스템 구현: 백엔드 및 모바일 애플리케이션 청사진
본 섹션에서는 아키텍처를 서버부터 클라이언트까지 전체 기술 스택을 포괄하는 구체적인 구현 계획으로 전환합니다.

### 4.1. 백엔드 기술 스택
언어/프레임워크: LangChain/LangGraph의 기본 언어인 Python을 사용합니다. API 엔드포인트를 노출하기 위해    

FastAPI 또는 Flask와 같은 웹 프레임워크를 활용합니다.

멀티 에이전트 엔진: 상태 관리 및 오케스트레이션을 위해 LangGraph를 사용합니다.   

영속성 (Persistence): 토론 상태가 저장되고 복구될 수 있도록 LangGraph의 checkpointer 기능을 구현하기 위해 PostgreSQL과 같은 데이터베이스나 Redis와 같은 키-값 저장소를 사용합니다.   

### 4.2. 실시간 통신: 서버-전송 이벤트 (Server-Sent Events, SSE)
WebSocket과 SSE를 비교 분석한 결과, WebSocket은 이 사용 사례에 비해 과도하게 복잡한 완전 양방향(full-duplex) 통신을 제공합니다. 토론 스트림은 본질적으로 서버에서 클라이언트로의 단방향 통신입니다.   

따라서 SSE가 최적의 선택입니다. SSE는 구현이 더 간단하고, 표준 HTTP/S를 통해 작동하여 방화벽 문제를 피할 수 있으며, 브라우저에 재연결 기능이 내장되어 있고, 서버 리소스를 덜 소모합니다. 백엔드는 모바일 클라이언트가 구독하는 SSE 스트림을 열고, 각 에이전트의 응답을 새로운 이벤트로 푸시합니다.   

### 4.3. API 설계
애플리케이션이 작동하는 데 필요한 RESTful API 엔드포인트를 정의합니다. 명확한 API 계약은 통합 오류를 방지하고 프론트엔드와 백엔드의 병렬 개발을 가속화하는 데 필수적입니다.

### 4.4. 모바일 애플리케이션 (Android/iOS)
안드로이드와 아이폰을 한번에 관리 가능한 구성으로 개발합니다.

주요 구성 요소:

UI: 사용자가 6개 에이전트의 '아바타'를 보고 그들의 메시지가 실시간으로 나타나는 것을 볼 수 있는 깔끔한 채팅 형식의 인터페이스.

SSE 클라이언트: 토론 스트림을 구독하고 새로운 메시지가 도착할 때마다 UI를 업데이트하는 네이티브 SSE 클라이언트 구현.

시각화를 위한 WebView: 최종 인터랙티브 시각화를 렌더링하기 위해 D3.js 라이브러리를 사용하는 내장 WebView.

상태 관리: 앱은 토론의 상태(진행 중, 완료됨, 결과 사용 가능)를 효과적으로 관리해야 합니다.

## 섹션 5: 결과물 종합: 요약 및 시각화
본 섹션에서는 복잡한 토론 기록을 사용자에게 명확하고 가치 있으며 매력적인 결과물로 변환하는 중요한 마지막 단계에 초점을 맞춥니다.

### 5.1. 고급 요약 전략: 하이브리드 Map-Reduce 및 Refine
6개의 다른 페르소나를 포함하는 전체 토론 기록은 단일 LLM 호출의 컨텍스트 창을 초과할 것이므로, 간단한 stuff 체인은 사용할 수 없습니다.   

map-reduce 방식은 병렬 처리로 빠르고 확장 가능하지만 토론의 서사적 흐름을 잃을 수 있으며 ,    

refine 방식은 일관된 서사를 구축하는 데 탁월하지만 느리고 순차적입니다.   

이 문제에 대한 해결책으로 2단계 하이브리드 접근법을 제안합니다.

Map 단계: 토론 기록을 대화 턴(turn) 단위로 분할합니다. LLM 체인을 이 청크들에 매핑하여 각 교환에 대한 간결한 요약을 생성합니다. 이 단계는 빠르고 병렬화가 가능합니다.

Refine 단계: Map 단계에서 생성된 요약들을 순차적으로 refine 체인에 공급합니다. 이 체인은 아이디어가 어떻게 탄생하고, 도전을 받고, 지지를 얻어 최종 결론에 통합되었는지 등 토론의 논리적 진행 과정을 보존하는 일관된 최종 요약을 구축합니다. 이는 두 방법의 장점을 결합한 접근법입니다.

### 5.2. 데이터 시각화: D3.js를 이용한 인터랙티브 논증 맵
다양한 JavaScript 시각화 라이브러리 검토 결과 , GoJS 나 Cytoscape.js 와 같은 라이브러리도 훌륭하지만, 애플리케이션의 고유한 요구사항에 완벽하게 부합하는 맞춤형 시각화를 제작할 수 있는 독보적인 유연성을 제공하는    

D3.js를 권장합니다.   

구현:

백엔드 데이터 구조화: 토론이 끝나면 백엔드는 최종 기록을 방향성 그래프(directed graph)를 나타내는 구조화된 JSON 객체로 처리합니다. 각 노드는 에이전트의 발언을 나타내며 agent_id, hat_color, mbti_type, statement_text, turn_number와 같은 메타데이터를 포함합니다. 엣지는 발언들이 어떤 발언에 대한 응답인지를 연결합니다.

프론트엔드 렌더링: 모바일 앱의 WebView는 D3.js 라이브러리가 포함된 페이지를 로드합니다. D3.js는 이 JSON 데이터를 파싱하여 인터랙티브 SVG로 렌더링합니다. 사용자는 패닝, 줌, 노드 탭을 통해 세부 정보를 탐색할 수 있습니다.

### 5.3. AI 추론 과정을 위한 진단 도구로서의 시각화
시각화는 단순한 요약을 넘어 '설명 가능한 AI(Explainable AI, XAI)'를 위한 도구로서 기능할 수 있습니다. 이는 사용자가 AI의 추론 과정을 시각적으로 감사할 수 있게 해줍니다. 시각화의 구조 자체는 토론의 지적 여정을 강조하도록 설계되어야 합니다.

이러한 설계의 배경은 다음과 같습니다. 사용자의 요구는 '시각화된 콘텐츠 요약'이지만, 이 앱의 핵심 가치는 여섯 색깔 모자 토론의 과정 자체에 있습니다. 따라서 시각화는 무엇이 논의되었는지를 넘어 어떻게 논의가 전개되었는지를 보여주어야 합니다. 결과물을 논증 그래프(노드는 발언, 엣지는 응답)로 구조화함으로써 논리의 흐름을 시각화할 수 있습니다.   

여기에 시각적 단서를 추가하여 의미의 층위를 더할 수 있습니다. 노드를 모자 색상으로 구분하고, MBTI 사분면에 따라 다른 노드 모양을 사용하며, 발언의 영향력(예: 얼마나 많은 응답을 생성했는지)에 따라 노드 크기를 조절하는 것입니다. 이 접근법은 시각화를 단순한 요약에서 강력하고 탐색 가능한 인터페이스로 변환합니다. 사용자는 "여기에 초록 모자의 창의적인 아이디어가 있고", "검은 모자가 이를 어떻게 반박했으며", "하얀 모자가 갈등을 해결하기 위해 어떤 데이터를 제공했는지"를 즉시 확인할 수 있습니다. 이는 AI의 협력적 문제 해결 과정에 대한 깊은 통찰력을 제공하고 사용자 신뢰를 구축합니다.

## 섹션 6: 전략적 권장 사항 및 향후 로드맵
본 마지막 섹션에서는 프로젝트를 운영하기 위한 지침을 제공하고 향후 발전을 위한 경로를 제시합니다.

### 6.1. 배포 및 확장성
도커로 이미지를 말아서 홈서버에서 배포하려고 합니다.

### 6.2. 보안 및 인증 (Authentication & Authorization)

MVP 단계: 개인 개발 특성을 고려하여 인증 절차를 생략하고, 세션마다 5개의 코인을 무료 제공하는 방식으로 운영합니다.

확장 단계: MVP 검증 이후 수익성이 확보되면 SNS 로그인(OAuth2 기반) 기능을 추가하고, 사용자 계정을 통한 사용량 추적 및 결제 시스템을 연동합니다.

### 6.3. 비용 관리 및 LLM 호출 최적화

MVP 단계: 비용 제약을 고려하지 않고 최고의 품질을 내는 답변에 집중합니다.

확장 단계: 사용자가 감당 가능한 비용 구조를 찾기 위해 토큰 사용량 분석, 요약 기반 context 축소, 모델 크기별 적응형 호출 전략을 적용합니다.

### 6.4. 실패 처리 및 복구 전략

MVP 단계: 실패 시 단순히 “죄송합니다, 답변을 생성하지 못했습니다” 와 같은 fallback 메시지를 출력합니다.

확장 단계: 재시도 정책, Tool 장애 대응, 부분 응답 허용 등 정교한 복구 전략을 도입합니다.

### 6.5. UX 전략

MVP 단계: 6개의 모자가 번갈아 등장하는 단톡방(그룹 채팅) 형태 UI로 구현합니다. 사용자는 일방적으로 답변을 받아볼 수 있습니다.

확장 단계: 사용자가 직접 파란 모자 역할을 맡거나, 특정 모자의 개입 순서를 지정하는 등 사용자 개입 포인트를 추가합니다.

### 6.6. 데이터 및 프롬프트 관리

프롬프트는 전용 폴더에 관리하며, 버전 관리를 통해 히스토리를 추적합니다.

향후 프롬프트 레지스트리/설정 파일 기반 관리로 확장 가능성을 열어둡니다.

### 6.7. 멀티모달 입력

계획 없음. 본 프로젝트는 텍스트 기반 입력/출력에만 집중합니다.

### 6.8. 사용자 타겟

일반 사용자를 대상으로 하는 창의적 사고 지원 도구를 목표로 합니다.

회의 지원/기업형 도구로의 확장은 2차 로드맵 단계에서 고려합니다.

### 6.9. 토론 종료 조건

충분히 품질이 높은 답변의 기준은 다음과 같습니다.

예: 사용자가 “6개의 모자 기법을 활용한 애플리케이션 만들고 싶어” 라고 입력했을 때,

시스템은 “# Six Sorting Hat - 육모자 애플리케이션 구현 기획” 수준의 문서 초안을 완성해야 합니다.

### 6.10. 실시간성 수준

턴 기반 순차 답변 구조를 유지합니다.

각 모자의 발언이 순서대로 출력되며, SSE를 통해 실시간 스트리밍됩니다.

### 6.11. 시각화 범위

최종 토론이 종료된 후, 최종 그래프만을 시각화합니다.

중간 진행 과정은 시각화하지 않으며, 결과물 중심의 D3.js 기반 논증 그래프를 제공합니다.

### 6.12. 품질 관리 및 Observability

LangSmith를 도입하여 LLM 응답 품질 추적, 체인 실행 디버깅, 사용자 세션 분석을 지원합니다.

자동화된 품질 지표(일관성 점수 등)와 휴먼 평가를 병행하여 토론 품질을 평가합니다.
