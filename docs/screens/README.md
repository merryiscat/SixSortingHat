# 화면 기획 규약

SixSortingHat 챗봇의 흑백 와이어프레임 작업 규약. `screen-plan` 스킬은 시각 규칙·구조를
책임지고, **도메인 어휘는 이 문서가 권위**다. 화면을 새로 그리거나 고치기 전에 반드시 읽는다.

## 전제

- 반응형 웹, **모바일 우선** (375 default → 768 → 1024)
- **개입형** — 토론 중 사용자가 질문을 추가하거나 특정 모자를 지목할 수 있다
- 화면 경로는 `docs/screens/` 로 고정

## 영역 prefix

| Prefix | 영역 | 화면 |
|---|---|---|
| I | 입력 / 시작 | I1 주제 입력 |
| D | 토론 (Discussion) | D1 토론 진행 |
| R | 결과 (Result) | R1 결과·요약 |
| H | 기록 (History) | H1 토론 기록 |
| S | 설정 (Settings) | S1 설정 |

ID·이름·목적은 1:1 고유. 다른 화면에서 참조할 때는 ID로만 호출한다.
새 영역이 필요하면 prefix를 추가하고 이 표를 갱신한다.

## 모자 명칭 — 고정

**하양 / 빨강 / 검정 / 노랑 / 초록 / 파랑** 6개만 사용한다.
`README.md`(프로젝트 루트)가 원천이며, 임의 별칭("비평가", "낙관이", "아이디어맨" 등)을
만들지 않는다.

역할 라벨도 아래로 고정한다. 화면에서는 모자명 + 역할 라벨을 함께 노출한다.

| 모자 | 역할 라벨 |
|---|---|
| 하양 | 사실·정보 |
| 빨강 | 감정·직관 |
| 검정 | 위험·비판 |
| 노랑 | 이점·기회 |
| 초록 | 창의·대안 |
| 파랑 | 진행·종합 |

**파랑은 다른 5개와 동급이 아니다.** 토론을 지휘하고 평가하는 역할이므로,
화면에서도 나머지 5개와 시각적으로 명확히 구분되어야 한다. 5개와 같은 줄·같은 카드
스타일로 나열하면 안 된다.

## 토론 진행 구조 (핵심 도메인 규칙)

화면의 기본 단위는 "모자의 발언"이 아니라 **의견 하나**다. 의견 하나가 아래 사이클을 돈다.

**파랑은 의견을 제시하지 않는다.** 의견을 내는 것은 하양·빨강·검정·노랑·초록 5개이고,
파랑은 지명·평가·종합만 한다. 따라서 한 의견의 평가자는 **제안자를 뺀 4개 모자**다.

```
파랑이 모자 지명 (하양·빨강·검정·노랑·초록 중)
  └ 지명된 모자가 의견 제시
      └ 제안자를 뺀 4개 모자가 그 의견에 평가 점수 (0~10)
          └ 파랑이 종합 점수 부여 (0~10)
              └ 분기 ┬ 사용자 발언 → 파랑이 검토 → 반영해서 다음 모자 지명
                     └ 사용자 발언 없음 → 파랑이 다음 모자 지명
```

### 의견의 본문 — 여러 블록

의견 하나는 텍스트 블록 **1~4개**로 이루어진다. 논지가 길어지면 한 덩어리로 쓰지 않고
블록을 나눠 쓴다. **블록이 여러 개여도 의견은 하나**이므로, 평가와 점수는 블록별이 아니라
**의견 전체에 한 번** 매겨진다.

### 점수 — 0~10

5개 모자의 평가와 파랑의 종합 점수 모두 **0~10 정수**다.
스케일이 확정되었으므로 와이어에는 대표 숫자를 직접 적는다 (토큰으로 가리지 않는다).
`/10` 표기는 파랑 판단에만 한 번 붙여 스케일을 알리고, 5개 평가에는 숫자만 적는다.

**파랑의 종합 점수는 다른 모자 점수의 평균이 아니다.** 다른 모자들의 평가를 *참고한*
파랑의 독자 판단이다. 화면에서 이것이 평균으로 오해되게 표시하면 안 된다 —
"평균", "합계", "총점" 같은 라벨을 쓰지 않고, 파랑 점수를 5개 점수와 다른 위계에 둔다.

### 사용자 발언의 효과

사용자 발언은 **이미 매겨진 점수를 바꾸지 않는다.** 파랑이 발언을 검토해서
**다음 의견을 낼 모자를 고르는 데** 반영한다. 즉 사용자는 점수를 흔드는 것이 아니라
토론의 방향을 튼다.

**미정** — 한 사이클이 끝난 뒤 모자를 탈락시킬지, 다른 방식을 쓸지는 아직 정해지지 않았다.
화면에 탈락 UI를 넣지 않는다. 종료 조건도 미정.

### 흑백 환경에서의 모자 구분

와이어는 색을 쓰지 않는다. 색상 대신 **라벨 + 보더 스타일 + 스와치 패턴**으로 구분한다
(`wireframe.css` 의 `.hat--*`).

| 모자 | 보더 | 스와치 |
|---|---|---|
| 하양 | 1px solid `--c-4` | 빈 사각 |
| 빨강 | 1px dashed `--c-2` | 사선 |
| 검정 | 2px solid `--c-0` | 채움 |
| 노랑 | 1px dotted `--c-2` | 점 |
| 초록 | 3px double `--c-2` | 격자 |
| 파랑 | 좌측 4px solid `--c-0` | 가로줄 |

## 데이터 토큰

사용자 데이터는 중괄호 토큰 + `.token` 클래스로 표기한다. 동일 의미는 동일 표기.

`{주제}` `{의견}` `{점수}` `{평가}` `{진행}` `{요약}` `{사이클}` `{날짜}` `{소요시간}` `{모자}` `{개입}`

- `{진행}` — 파랑의 진행 멘트.

- `{의견}` — 의견 본문 블록 하나. 한 의견에 1~4개가 붙는다.
- `{평가}` — 점수에 딸린 한 줄 근거.
- **점수는 토큰을 쓰지 않는다.** 0~10으로 확정되었으므로 대표 숫자를 직접 적는다.

## 비공개 필드 — 화면 노출 금지

내부 계산·운영용이므로 사용자에게 보이지 않는다.

- 프롬프트 원문
- 모델명, 토큰 수, 비용
- 발언 순서 결정 로직 (순서는 매 실행마다 달라지지만 그 이유를 노출하지 않는다)

> 점수는 비공개가 아니다. 5개 모자의 평가와 파랑의 종합 점수는 **화면의 핵심 요소**이므로
> 그대로 노출한다.

## 카피 규칙

- 라벨·수치 중심, **2~3단어**. 설명하려 하지 말고 구조로 전달한다
- 서술형·과잉 친절체 금지: "~하고 있어요", "~해 주세요", "당신만의 ~"
- 이모지·느낌표·감탄사 금지
- lorem ipsum 금지 — 실제 도메인 라벨만

### 상태 카피 고정

| 상태 | 카피 |
|---|---|
| 의견 생성 중 | `생성 중` |
| 다른 모자 평가 중 | `평가 중` |
| 파랑 종합 중 | `종합 중` |
| 파랑이 사용자 발언 검토 중 | `검토 중` |
| 파랑이 다음 모자 지명 | `다음` + 모자명 |
| 대기 | `대기` |
| 사용자 차례 | `내 차례` |
| 완료 | `완료` |
| 오류 | `실패` + `[다시]` |

## 작업 절차

새 화면: 기존 화면 전수 읽기 → 4안(`{ID}-options.html`) → 선택 → 확정(`{ID}.html`)
→ 사이드 노트(의도/대안/미정) → `index.html` 갱신 → **인접 화면 [다음] 메타 역방향 갱신**

메타는 항상 양방향으로 일치해야 한다. 한쪽에만 적혀 있으면 안 된다.

작성·수정 직후 브라우저로 띄워 **375×812 / 768×1024 / 1280×900** 3종을 함께 확인한다.
